# 学径正式产品进一步开发指南

**版本**：v0.1  
**日期**：2026-06-08  
**范围**：面向正式用户场景的后续开发，不以 Demo 数据完整性为讨论重点。

---

## 1. 当前测试结论

本轮以使用者视角重点测试了多模态能力，并复核了前一轮发现的产品闭环问题。整体判断：

- 多模态能力不是空壳。`/api/media/status` 能正确暴露文生图、视觉理解、视频生成状态。
- 已生成的 media 资源包含图片与视频资产，图片、视频读取接口均可正常返回。
- 前端媒体详情页能展示讲解视频、分镜幻灯片与 Markdown 正文。
- 聊天附件上传链路可用，支持图片保存、附件上下文构建、文件读取和不支持格式拦截。
- 正式产品还需要补齐质量控制、状态一致性、视觉理解失败处理、媒体资源去重展示和移动端适配。

## 2. 多模态测试记录

### 2.1 能力状态接口

测试接口：`GET /api/media/status`

通过项：

- `qwen_wanx` 文生图可用。
- `qwen_vl` 图片理解可用。
- `qwen_wanx_video` 图生/文生视频能力可用。
- Kimi 提示词优化状态可见。

改进点：

- 状态接口只说明“能力是否配置”，没有说明最近一次生成是否成功、平均耗时、失败原因分布。
- 建议增加 `last_success_at`、`last_error`、`avg_latency_ms`、`quota_hint` 等运行诊断字段。

### 2.2 媒体资源读取

测试对象：现有 `media` 类型资源。

通过项：

- 资源正文包含 4 张图片引用和 1 个 mp4 视频引用。
- `/api/media/images/{filename}` 返回 `image/jpeg`，文件大小正常。
- `/api/media/videos/{filename}` 返回 `video/mp4`，视频文件可读取。
- 前端 `<video>` 控件 `readyState=4`，说明浏览器可加载播放资源。

问题：

- 同一批图片既出现在顶部幻灯片，也继续出现在 Markdown 正文，用户会看到重复内容。
- 标题和主题出现“1 · 多模态讲解分镜”“学习主题：1”这类低质量元数据，说明生成主题提取或历史数据清洗不足。
- 正文里仍有“质检提示：与知识库重叠较低”，但页面没有把它提升为显眼的风险状态。

建议：

- `MediaResourceView` 在渲染正文前移除所有已被幻灯片消费的图片块，而不只移除封面。
- 资源标题、主题、来源库名称应进入统一的 `ResourceMetadata` 清洗流程。
- 质检失败或低置信度资源应在卡片和详情页顶部显示“需复核”状态。

### 2.3 聊天图片上传

测试接口：

- `POST /api/chat/attachments`
- `POST /api/chat/attachments/context`
- `GET /api/chat/attachments/{user_id}/{filename}`

通过项：

- 图片上传成功，返回 `kind=image`、`url`、`size`。
- 附件读取成功，鉴权生效。
- `.exe` 等不支持格式会返回 400，错误信息明确。
- 图片视觉理解失败时有兜底文案：“暂未能自动识别内容”。

问题：

- 极小图片无法识别时，`text_preview` 为空，前端用户不一定知道视觉理解是否执行过。
- 附件上传阶段会尝试视觉理解，但失败原因没有结构化返回。
- 聊天发送时的附件状态缺少“已识别 / 识别失败 / 仅作为文件上传”的用户可见标记。

建议：

- `ChatAttachmentMeta` 增加 `analysis_status`：`pending | success | failed | skipped`。
- 增加 `analysis_error_type`：`unsupported_image | provider_error | timeout | empty_result`。
- 前端附件卡显示识别状态，避免用户误以为图片已经被充分理解。

## 3. 正式产品优先级

### P0：闭环一致性

正式产品首先要保证用户看见的数据一致：

- 画像页生成画像后，评估页的画像完整度必须同步更新。
- 侧栏路径完成度、路径页总体进度、资源库当前阶段必须使用同一套计算函数。
- 资源完成、路径步骤完成、测验提交后，应统一触发画像、路径、评估的轻量刷新。

建议实现：

- 前端抽出 `computePathProgress(path)`，禁止各页面重复实现。
- 后端提供 `GET /api/dashboard/state/{user_id}`，一次返回 profile/resource/path/eval 的摘要。
- 所有学习事件写入后返回 `state_version`，前端发现版本变化再刷新相关模块。

### P0：多模态质量与降级

正式用户不会只关心“有没有图片/视频”，更关心是否可靠、可解释、可复用。

必须补齐：

- 生成进度：图片、视频、视觉理解都要有阶段事件。
- 失败降级：视频失败时明确回退到幻灯片；图片失败时明确回退到 SVG。
- 成本控制：视频生成必须可开关，并显示预计耗时。
- 质量标记：低置信度、无知识库支撑、视觉理解失败都应可见。

建议实现：

- 增加 `media_jobs` 表，记录 `job_id / user_id / resource_id / provider / status / error / assets_json / created_at`。
- 资源生成接口返回 `media_job_id`，前端轮询或 SSE 订阅进度。
- 媒体资源详情顶部展示资产状态：`视频已生成`、`配图 4/4`、`质检通过/需复核`。

### P1：对话指令遵循

测试中用户要求“三句话解释”，回复仍然偏长。正式产品中这会直接影响信任。

建议：

- 在 chat prompt 中显式加入用户格式约束提取，例如“几句话、列表、表格、不要展开”。
- 后处理阶段检测长度约束，超出时自动压缩。
- 前端提供“简洁 / 标准 / 详细”回复模式，而不是只靠用户自然语言控制。

### P1：媒体展示体验

建议：

- 幻灯片与正文图片去重。
- 视频封面、加载中、加载失败状态要完整。
- 分镜图支持全屏查看。
- 图片 alt 文案应来自镜头描述，而不是资源标题重复拼接。
- Markdown 中 Mermaid 渲染失败时显示可读的流程列表。

### P1：可访问性与可测试性

测试发现多个纯图标按钮没有可访问名称。

建议：

- 所有图标按钮必须有 `aria-label` 或 Tooltip。
- 给主流程元素增加稳定 `data-testid`，便于 E2E 测试。
- 聊天输入、发送、上传、资源卡操作、路径完成按钮优先补齐。

### P2：移动端与响应式

移动端能加载，但存在横向溢出。

建议：

- 快捷标签自动换行或横向滚动容器化。
- 背景装饰元素限制在 `overflow: hidden` 容器内。
- 侧栏在窄屏切换为抽屉式导航。
- 媒体详情页视频和幻灯片使用固定 `aspect-ratio: 16 / 9`。

## 4. 推荐开发路线

### Sprint 1：状态一致性与测试基线

目标：让用户操作后的所有页面数据一致。

任务：

- 抽取统一路径进度计算。
- 修复画像刷新后评估页仍为 0% 的问题。
- 增加关键接口 E2E：登录、上传附件、发送带附件消息、打开 media 资源、标记路径完成。
- 为主流程按钮补 `aria-label` / `data-testid`。

验收：

- 任一学习事件发生后，侧栏、路径页、评估页进度一致。
- E2E 可稳定跑通核心链路。

### Sprint 2：多模态生成任务化

目标：让图片/视频生成可追踪、可恢复、可解释。

任务：

- 新增 `media_jobs` 持久化。
- 资源生成 SSE 输出 `image_start/image_done/video_start/video_done/fallback`。
- 前端展示媒体生成状态和失败原因。
- 媒体详情页去重展示图片。

验收：

- 视频生成失败时，用户能看到明确降级说明。
- 同一图片不会在幻灯片和正文重复出现。

### Sprint 3：回答质量与资源质检

目标：提高正式用户信任。

任务：

- 增加用户格式约束识别。
- 低置信度资源顶部展示风险状态。
- 资源质检结果结构化存储。
- Mermaid 渲染失败时降级为文字流程。

验收：

- “三句话解释”类请求不会输出长篇回答。
- 低置信度内容不会和普通内容以同样视觉权重展示。

### Sprint 4：正式产品体验

目标：从比赛演示走向可长期使用。

任务：

- 移动端主界面适配。
- 附件识别状态可见。
- 设置页收敛说明文字。
- 增加资源分享/导出时的资产打包能力。

验收：

- 390px 宽度下无主要内容横向溢出。
- 用户可以明确知道上传图片是否被模型理解。

## 6. 关键判断

后续开发不要继续单纯增加 Agent 数量或资源类型。当前更大的价值提升来自三件事：

1. **让状态一致**：用户不应在不同页面看到互相矛盾的数据。
2. **让多模态可信**：图片、视频、视觉理解都要有进度、失败原因和降级路径。
3. **让输出可控**：用户要求简洁时必须简洁，低置信度内容必须显性标注。

这些做好后，项目会从“功能很满的比赛作品”变成“可以让真实学习者持续使用的学习产品”。
